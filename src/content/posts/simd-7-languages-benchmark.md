先说一个反常识的结论：

你精心手写的 SIMD 代码，很可能比编译器自动生成的还慢。

这不是猜测，是我把 7 种语言拉到同一台机器上实测出来的。同一段循环、同一台机器、同一组数据：手写 AVX2 版本比纯标量快 12.7 倍；但同一份 C 代码，只把编译选项从 -O2 换成 -O3 -march=native，加速比是 1.00 倍，一点没变。

一个 12 倍，一个 1 倍，差在哪？

这篇不讲 SIMD 有多厉害，只讲一件更值钱的事：它什么时候完全不起作用，以及为什么。

## 一、先看结果：两个任务，天壤之别

我挑了两个最普通的数组浮点运算。

第一个是点积 dot：s = s + a[i] * b[i]。特点是"归约"——所有中间结果最后要汇总成一个数，涉及跨 lane 求和。

第二个是乘加 saxpy：y[i] = alpha * x[i] + y[i]。特点是"逐元素"——每个元素各算各的，互不相干。

看起来都是"在数组上做浮点运算"，可向量化的难度完全不是一个量级。

下面是同一份 C 代码、在同一台机器上、用四种方式编译的结果（数组长度 65536）：

| 编译方式 | dot 点积 | saxpy 乘加 |
| --- | --- | --- |
| 纯标量（禁向量化） | 0.0610 ms | 0.0241 ms |
| -O3 -march=native（自动向量化） | 0.0612 ms，1.00 倍 | 0.0084 ms，2.9 倍 |
| -O3 -march=native -ffast-math | 0.0063 ms，9.7 倍 | 0.0084 ms |
| 手写 AVX2 intrinsics | 0.0057 ms，10.7 倍 | 0.0072 ms |

看清楚这两列：dot 那列，自动向量化的收益是 1.00 倍——编译器忙活半天，什么都没快。saxpy 那列，同样的编译器，同样的选项，拿到了 2.9 倍。

同一份代码，为什么差别这么大？

![同一份 C 源码在四种编译方式下的耗时对比：dot 的自动向量化收益为 1.00 倍，saxpy 为 2.9 倍](/media/posts/simd-7-languages-benchmark/SIMD_C-f9c7c9ab.png)

## 二、为什么：一个"归约"决定成败

先说 SIMD 是什么。它做的事很简单：把 8 个数装进一个 256 位寄存器，一条指令同时算 8 个。普通标量指令一次只喂给 CPU 一个数，而 CPU 的浮点单元明明很宽——256 位甚至 512 位的运算单元，标量指令只用到 32 位。

所以理论上，float32 在 AVX2（256 位）上的理想加速是 8 倍。可这个 8 倍经常拿不满，第一道坎就是"归约"。

![标量执行逐格推进、一条指令处理一个数；向量执行一条指令覆盖全部八个 lane](/media/posts/simd-7-languages-benchmark/SIMD_-35e90229.gif)

关键要看编译器的报告和真实性能对不对得上。gcc 加 -fopt-info-vec-optimized 会告诉你哪些循环向量化了：

```
simd_bench.c:49:5: note: loop vectorized      ← dot 的点积循环
simd_bench.c:54:5: note: loop vectorized      ← saxpy 的乘加循环
```

报告说两个循环都向量化了。但性能数据说 dot 一点没变。

报告没有骗人，只是"向量化"不等于"快"。看反汇编就明白了：

```
vmulps  -0x40(%r9),%xmm4,%xmm1     ; 乘法确实向量化了
vaddss  %xmm1,%xmm0,%xmm0          ; 但归约是标量加！
vshufps $0x55,%xmm1,%xmm1,%xmm2    ; 还要 shuffle 把 lane 抠出来
vaddss  %xmm2,%xmm0,%xmm0
vunpckhps %xmm1,%xmm1,%xmm2
vshufps $0xff,%xmm1,%xmm1,%xmm1
vaddss  %xmm2,%xmm0,%xmm0
vaddss  %xmm1,%xmm0,%xmm0
```

乘法用上了向量指令 vmulps，可归约部分是一路标量加法 vaddss，还夹着一堆 shuffle 搬运。向量化省下的时间，全被这个"水平归约"吃回去了。

![dot 归约为何吃掉向量化收益：乘法两边都向量化了，差别在乘法之后——归约要多走八步标量操作](/media/posts/simd-7-languages-benchmark/SIMD_-79664a9a.gif)

根因是浮点加法不满足结合律。(a + b) + c 和 a + (b + c) 在浮点里结果可能不同。C/C++ 的标准建立在 IEEE 754 之上，要求编译器保持求值顺序。所以编译器不能把"逐个累加"改成"先分别累加到 8 个向量累加器再合并"——那会改变结果。在正确性和性能之间，编译器默认选正确性。

那加上 -ffast-math 呢？性能立刻从 0.0612 ms 变成 0.0063 ms，9.7 倍。代价是结果不再逐位可复现：

| 编译方式 | dot 的 checksum |
| --- | --- |
| 纯标量 | 216032526.8555 |
| -O3 -march=native | 216032526.8555（逐位相同） |
| -O3 -march=native -ffast-math | 216032270.5078（变了） |

对图形、统计、机器学习，这点误差无所谓；对财务计算、需要审计、要求结果可复现的场景，就是灾难。这也是 Java 的 Vector API 在官方提案里明确写的：它不保证支持严格浮点运算。

所以判据其实很简单，就一句话：**看循环里有没有把多个元素合并成一个值的操作。**

有（求和、点积、求最大值）——那就是归约，自动向量化默认失效。
没有（每个元素各算各的）——编译器大概率能自己搞定。

这一条，比记住任何一条 intrinsic 都有用。

## 三、三个容易踩的坑

第一，有 AVX-512 不等于更快。部分 Intel 芯片跑 AVX-512 时会降频，轻负载下反而比 AVX2 慢。所以 Java 的 FloatVector.SPECIES_PREFERRED 在某些机器上会主动选 256 位——它承诺的是"推荐"宽度，不保证给你最宽的。

第二，编译期和运行期是两回事。-march=native 在你自己的机器上编译、部署到不支持该指令集的机器，程序会直接崩（SIGILL）。生产环境要用 -mavx2 这类明确目标，或者做运行期分发。

第三，虚拟机不保证透传。云厂商的 CPU 会换，今天这台有 AVX2，明天调度到另一台可能就没有。依赖特定指令集的功能，必须做能力探测。

顺便说一个云上的现实：我测试机上执行 cat /proc/cpuinfo，CPU 型号显示的是 "General Processors"——真实型号被虚拟化层抹掉了。在云上你只能靠 flags 反推能力，根本看不到具体是哪个型号的芯片。

![向量寄存器宽度阶梯：SSE 与 NEON 为 128 位、AVX2 为 256 位、AVX-512 为 512 位、SVE 可变，本次测试机落在 AVX2 档](/media/posts/simd-7-languages-benchmark/SIMD_-0383b1d5.png)

## 四、真正的天花板不是宽度，是内存带宽

即使是手写、完美的 SIMD，收益也不是常数。同一份点积代码，跑在三种数据规模上：

| 规模 | 数据量 | 标量 | 手写 AVX2 | 加速比 |
| --- | --- | --- | --- | --- |
| 4096 | 32 KB，L1 内 | 0.0038 ms | 0.0003 ms | 12.7 倍 |
| 65536 | 512 KB，L2 内 | 0.0610 ms | 0.0057 ms | 10.7 倍 |
| 1000 万 | 80 MB，主存 | 9.4194 ms | 2.4668 ms | 3.8 倍 |

从 12.7 倍掉到 3.8 倍。换成吞吐更直观：数据在主存时，AVX2 版跑出 32.4 GB/s——已经顶到单核内存带宽附近。8 倍宽度，最后只兑现 3.8 倍，卡在带宽上。

所以优化顺序应该是：先问数据在不在缓存里（分块、提高局部性，收益常常大于 SIMD），再看循环能不能向量化，最后才考虑手写 intrinsics。反过来做，就是在内存墙上撞头。

![加速比随数据规模衰减：L1 里 12.7 倍、L2 里 10.7 倍、主存里只剩 3.8 倍](/media/posts/simd-7-languages-benchmark/SIMD_-d11e0d9a.png)

## 五、7 种语言的真实战绩

### 先说数据为什么可信

所有语言都用同一组输入（同一个 xorshift32 序列，种子 12345）、同一个算法。既然数据一样、算法一样，那算出来的 checksum 应该对得上：

| 实现策略 | checksum | 一致的语言 |
| --- | --- | --- |
| 标量顺序累加 | 216032526.8555 | C / Rust / Java / Go 逐位相同 |
| 8-lane 向量累加 | 216032270.5078 | C / Rust / Java / Go 逐位相同 |

两个数字完全对齐，证明这些语言算的确实是同一个东西，性能差异不是"算的内容不一样"造成的。

### 点积最快能到多少（长度 65536）

| 语言 | 最快实现 | 耗时 | 相对该语言标量 |
| --- | --- | --- | --- |
| C | 手写 AVX2 | 0.0057 ms | 10.7 倍 |
| Rust | 手写 AVX2 | 0.0061 ms | 10.0 倍 |
| Python | numpy | 0.0080 ms | 374 倍（对比纯循环） |
| Java | Vector API | 0.0105 ms | 5.8 倍 |
| Go | simd 包 | 0.0205 ms | 3.0 倍 |
| Node | 无 | 0.0617 ms | 1.0 倍 |

![七种语言 dot 点积最快实现的横向对比：C 与 Rust 站在同一档，Java 的 Vector API 拿到一半，Go 的实验性 SIMD 不到 C 的三分之一](/media/posts/simd-7-languages-benchmark/SIMD_-dot-49fd20db.png)

### 三个最反常识的发现

第一，Rust 的手写 SIMD 已经"无利可图"。看乘加那一项：Rust 标量 0.0068 ms，手写 AVX2 是 0.0080 ms——手写反而更慢。因为 LLVM 的自动向量化已经把这个逐元素循环做到位了，你再手写一遍，只是把编译器做过的事重做。Rust 的优势在归约场景，点积手写能拿到 4.1 倍，是所有语言里最快的。

第二，Java 的 Vector API 用对地方才快。同样是 Java：乘加场景，标量 0.0066 ms，Vector API 是 0.0080 ms，反而慢；点积场景，标量 0.0611 ms，Vector API 是 0.0105 ms，快 5.8 倍。因为 HotSpot 的 C2 编译器早就把逐元素循环自动向量化了，你再套一层 Vector API，多出来的结构成了开销。而点积是归约，C2 搞不定。所以"用了 Vector API 就更快"是错觉。

第三，Python 的 374 倍最容易被误读。纯 Python 循环 2.9923 ms，numpy 0.0080 ms，差了 374 倍。但这不是"Python 学会 SIMD 了"——numpy 快，是因为 np.dot 内部调的是用 C 写好的、已经向量化的库。Python 本身依然没有任何 SIMD 能力，你写 for 循环就是在解释器里逐个跑字节码，谁来都救不了。唯一的正确答案是：把计算推给 numpy 或 torch，别自己写循环。

（另外补一句方法学教训：第一次采集时 Rust 的点积测出 23.22 ms，比 C 慢 2.5 倍。反汇编后发现两者循环体几乎完全相同。重测稳定在 9.41 ms——那个数是瞬时干扰。单次跑出的数字不能直接采信。）

## 六、Java 人到底该怎么选

Java 这里的选择最多，也最容易选错。

方案一，Vector API。它能让你不写死指令集，一份源码在 x64 上跑 8 lane、在 ARM 上跑 4 lane，宽度由运行期决定。但它从 JDK 16 孵化到现在（JDK 27 是第十二次孵化），一直是 incubating 状态，要用还得加启动参数，官方说要等值类型项目落地才转正，短期别指望它变成正式 API。实测收益：归约场景 5.8 倍，逐元素场景没收益。

方案二，用 FFM API 调 native SIMD。JDK 22 起可用，不用 JNI 就能调 C 库。关键是算清楚调用开销：kernel 是微秒级的（大数组）就划算；kernel 只有几百纳秒（比如 768 维向量点积），跨界的几十纳秒能吃掉三分之一收益。

方案三，调 BLAS（OpenBLAS、MKL 这些）。矩阵乘法、线性代数、FFT 这类成熟计算，这些库是几十年优化出来的，你自己写不可能更好。

方案四，什么都不做，靠 JDK 内部向量化。Arrays.equals、Arrays.mismatch、String.indexOf、System.arraycopy 这些高频方法，JDK 内部早就有手写 intrinsic 了，你调用它们就自动享受到了，比自己在 Java 层写循环快得多。先查 JDK 有没有现成方法，往往比自己写 Vector API 更划算。

一句话决策：先查标准库有没有现成方法；矩阵计算调 BLAS；归约/相似度计算上 Vector API；简单逐元素循环先测标量版，很可能 JIT 已经代劳；数据量小于几百元素就别折腾了。

## 七、带走这张清单

别急着写 intrinsics，先按这个顺序问自己三个问题：

第一，数据在缓存里吗？不在的话，先做分块、提高局部性，这一步的收益常常大于 SIMD。

第二，循环里有归约吗？有，自动向量化默认失效，要么放开浮点严格性（如果精度允许），要么用高级 API 或手写；没有，编译器很可能已经代劳，先测标量版。

第三，热点占比多少？不明确就先去 profile。SIMD 是最后一步，不是第一步。

最后记住三句话：

能不能向量化，先看循环里有没有归约。这是全文最实用的一条判据。

向量宽度给的是理论倍数，内存带宽才是实际上限。同一个核，数据在 L1 里能拿 12.7 倍，在主存里只剩 3.8 倍。

先测，再判断。Rust 和 Java 的"标量版"早就被自动向量化了，手写反而更慢。"用了 SIMD 就更快"是错觉。
